The Architecture

Six-layer reactive pipeline

Every element's position is a live expression over other elements' measured bounds — not a hardcoded value.

time
→
animations
→
measurements
→
constraints
→
render

C(t) — the constraint layer — is defined in terms of M(t) (measured bounds of other elements), not t directly.
So subtitle.y = title.bounds.bottom + 16 re-evaluates every frame as the title grows.

Four Phases

From signals to authoring

Each phase builds on the last. All demos are self-contained HTML files — no build step.

Phase 1 Interactive Signals

Any signal — mouse, scroll, viewport, time, custom — becomes a root of the constraint graph. Elements constrain their position based on other elements' live measured bounds, which themselves depend on signals.

mouse.x → box0.x → box0.bounds.right → box1.x → … → box5.x
1 signal drives 16 constraint resolutions per frame

CSS and GSAP can animate on scroll. They can't express "element B's position is a function of element A's rendered bounds which depends on the mouse." That cross-element measurement dependency is the differentiator.

Phase 2 Agent Negotiation

Claude receives the current spec + a natural language instruction, generates a JSON command array, executes against the live engine, receives violation feedback, and corrects — up to 3 rounds.

"make the dot follow the mouse"
→ {target:"dot", x:"mouse.x", y:"mouse.y"}
→ applied, 0 violations, resolved in 1 round

Key discovery: agents generate conditional expressions, not hardcoded positions. Given "label on whichever side has more space", Claude writes a live ternary that evaluates geometry every frame.

Phase 3 Semantic Intents

Intents are stored as living relationships — natural language paired with a compiled constraint expression. Three types: reactive (never stale), directional (may need re-compile when layout shifts), and measure (tracks actual rendered dimensions).

"subtitle always 16px below title"
→ stored as: subtitle.y = title.bounds.bottom + 16
→ title grows → subtitle follows automatically

The registry knows why each element is where it is. Directional intents go stale when their dependency moves significantly — a re-compile button fetches new geometry and rewrites the expression.

Phase 4 Authoring Surface

The canvas becomes directly manipulable. Click to select any element — the inspector shows live measurements updating every frame. Drag to move — constraints propagate immediately. Type an intent — constraint arrows appear on the SVG overlay.

Select element → "always centered inside the hero box"
→ two constraints applied
→ green reactive arrows: hero_box → dot

Agents and humans share the same canvas. The agent's output is a living constraint the human can inspect, drag against, and override. The SVG overlay makes the constraint graph visible.

Constraint Expression Syntax
// Expressions are strings evaluated against live measurements + signals // Element measurements "title.bounds.bottom + 16" // reactive: re-evaluates every frame "hero_box.centerX" // tracks center of another element "title.actualWidth" // actual rendered text width // Slide pseudo-element (always available) "slide.centerX - 250" // center on slide "slide.width * 0.6 - 40" // proportional sizing // Interactive signals "mouse.x + 100 * cos(time.ms * 0.001)" // orbit "clamp(scroll.y / 200, 0, 1)" // scroll-driven opacity // Ternary — agents generate these natively "hero_box.bounds.left > slide.width - hero_box.bounds.right" " ? hero_box.bounds.left - label.width - 12" // left side has more space " : hero_box.bounds.right + 12" // right side has more space // Math: sin, cos, sqrt, pow, clamp, lerp, midpoint, abs, min, max
